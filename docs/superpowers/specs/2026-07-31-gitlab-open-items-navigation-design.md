# GitLab Open Issue/MR 快速导航设计

## 1. 背景与目标

现有扩展会在 GitLab Issue 或 Merge Request（MR）详情页顶部固定显示当前编号，
并提供独立的快速复制按钮。本次增加项目内 Open Issue 和 Open MR 的快速导航，
让用户在不打开列表页、不进行额外搜索的情况下，直接从当前编号进入其他条目。

本次功能的目标是：

- 在当前编号区域悬停时自动打开导航列表，减少一次点击。
- 只展示当前项目中状态为 Open 的 Issue 和 MR。
- 按 Issue、MR 两组展示，避免两类编号混淆。
- 点击其他条目后，在当前标签页跳转到对应详情页。
- 当前正在查看的条目在列表中高亮，但不可点击、不可再次跳转。
- 提供明确的“刷新列表”操作，允许用户绕过缓存获取最新数据。
- 延续现有自建 GitLab、SPA 导航、浅色/深色主题和无障碍支持。

## 2. 范围与边界

### 2.1 支持范围

导航入口仅出现在扩展已经识别的有效 Issue/MR 详情页。当前页面 URL 用于解析：

- GitLab 实例 origin。
- 当前项目的完整路径，支持多层 namespace。
- 当前资源类型：Issue 或 MR。
- 当前资源 IID。

菜单中的条目只属于当前项目，不跨项目、不跨 GitLab 实例展示。

### 2.2 Open 条目规则

- Issue 请求使用 `state=opened`。
- MR 请求使用 `state=opened`。
- 已关闭、已合并或其他非 Open 状态的条目不加入列表。
- 如果用户当前正在查看一个已关闭或已合并条目，该条目仍正常显示在顶部固定标签中，
  但不会被额外塞进 Open 列表，也不会出现“当前”高亮行。
- Open 列表为空时，Issue 和 MR 分组仍然显示，并分别展示对应的空状态。

### 2.3 明确不做

本次不增加：

- 全局 GitLab 实例范围的跨项目搜索。
- Access Token、账号配置或独立设置页。
- 搜索输入框、过滤器、排序切换或分页控件。
- Closed、Merged、Draft 等非 Open 条目混入列表。
- 新的扩展权限、后台 Service Worker、持久化缓存或统计上报。

## 3. 方案选择

采用当前 GitLab 项目 REST API 加当前登录会话 Cookie 的方案：

```text
GET /api/v4/projects/<url-encoded-project-path>/issues
    ?state=opened&scope=all&order_by=updated_at&sort=desc&per_page=100

GET /api/v4/projects/<url-encoded-project-path>/merge_requests
    ?state=opened&scope=all&order_by=updated_at&sort=desc&per_page=100
```

Issue 和 MR 请求并行发起，使用浏览器当前页面的同源登录会话。相较于解析 GitLab
列表页 HTML，REST API 的字段和分页协议更稳定；相较于 GraphQL，REST API 对不同版本
的自建 GitLab 更容易兼容，且不需要额外的查询结构。

请求只发往当前页面的 origin，使用当前用户已有的 GitLab 权限。扩展不读取、保存或
上传认证信息，也不申请 `cookies`、`storage`、`tabs` 或 `identity` 权限。

## 4. 数据模型与请求流程

### 4.1 项目上下文

解析器在保留现有 `kind` 和 `iid` 的基础上，补充项目上下文：

```js
{
  origin: 'https://gitlab.example.com',
  projectPath: 'group/subgroup/project',
  kind: 'issue',
  iid: '8'
}
```

`projectPath` 来自资源路径之前的所有非空 URL segment。解析时分别对每个原始 segment
调用一次 `decodeURIComponent`，任一 segment 无法解码时将当前 URL 视为不支持；随后用
`/` 连接各 segment。构造 API URL 时仅对连接后的 `projectPath` 调用一次
`encodeURIComponent`，避免重复编码，并保证多层 namespace 和特殊字符不会改变 API
路径边界。
跳转地址使用当前 origin、项目路径和 GitLab 标准详情页路径构造：

```text
<origin>/<projectPath>/-/issues/<iid>
<origin>/<projectPath>/-/merge_requests/<iid>
```

### 4.2 API 响应映射

列表项只保留渲染和跳转必需字段：

```js
{
  kind: 'issue' | 'merge-request',
  iid: '8',
  title: '手写 HTTP 并发不健壮',
  webUrl: 'https://gitlab.example.com/group/project/-/issues/8'
}
```

优先使用 API 返回的 `web_url`；如果返回值缺失，则使用当前 origin 和项目路径
构造同等详情页地址。标题仅作为列表摘要显示，不读取正文、评论或用户资料。

### 4.3 分页

每个资源类型独立分页，首请求使用 `per_page=100`。如果响应头的 `X-Next-Page`
包含下一页编号，则继续请求，直到没有下一页。Issue 和 MR 请求用
`Promise.allSettled` 等价流程并行执行：只有两组及其全部分页都成功时，才合并并写入
一个完整项目快照。初次加载时如果仅一组成功，立即展示该组结果，失败组显示行内错误，
但不缓存这份部分结果。

### 4.4 加载时机

- 首次悬停、键盘聚焦或触摸打开菜单时开始加载。
- Issue 和 MR 请求并行执行。
- 请求期间在两个分组内分别显示“正在加载”。
- 菜单打开期间不重复发起同一项目的请求。
- 页面切换到同项目其他详情页时复用已有快照；切换到其他项目时丢弃旧快照。

## 5. 缓存与刷新

### 5.1 内存缓存

缓存仅存在当前内容脚本生命周期内，默认有效期为 60 秒。缓存键固定为：

```text
<origin> + <projectPath>
```

60 秒内再次打开菜单直接使用快照，不发起网络请求。缓存过期后，下一次打开触发
后台刷新；如果仍有可用旧快照，先显示旧列表，再在请求完成后替换为新列表。

### 5.2 刷新列表

弹层标题栏右侧固定显示“刷新列表”按钮及刷新图标：

- 点击后绕过 60 秒缓存，重新并行请求 Issue 和 MR。
- 刷新期间保留已有列表，刷新图标旋转，并为刷新按钮设置 `aria-busy="true"`。
- Issue 和 MR 都刷新成功后才替换列表，并清除已有错误提示。
- 已有完整快照时，任一组刷新失败都保留整份旧快照，并在标题栏下方显示
  “刷新失败，显示上次结果”。
- 没有旧数据时，每组独立显示结果或“无法加载”，成功组仍可正常使用；标题栏保留
  刷新入口，点击后同时重试两组。
- 刷新按钮本身不触发菜单关闭，也不触发条目跳转。

## 6. 用户界面与交互

### 6.1 固定标签结构

标签从左到右保持以下结构：

```text
[ Issue #8 ][复制图标]
```

- 移除插件自己的下拉箭头。
- 编号区域是导航触发区，复制按钮仍是独立的复制操作区。
- 复制按钮继续沿用 GitHub Octicon、Tooltip 和成功后绿色对勾，不改变既有行为。
- 导航菜单锚定在编号区域下方，不覆盖复制按钮。

### 6.2 打开与关闭

桌面鼠标行为：

- 鼠标进入编号区域后约 `150ms` 打开菜单。
- 鼠标从编号区域移动到菜单时保持菜单打开。
- 鼠标同时离开编号区域和菜单约 `250ms` 后关闭菜单。
- 鼠标进入菜单后取消关闭计时器。

键盘行为：

- 编号区域使用原生 `button`，通过 `aria-expanded` 和 `aria-controls` 关联导航弹层。
- 聚焦时打开菜单，并设置 `aria-expanded="true"`。
- 菜单关闭时，`Enter` 或 `Space` 打开菜单；菜单已打开时不反向关闭。
- `Escape` 关闭菜单并将焦点还给编号区域。
- 弹层不是 ARIA `menu`，不实现方向键模型或焦点陷阱；刷新按钮和可跳转条目按 DOM
  顺序加入标准 Tab 导航。
- 焦点位于编号按钮、复制按钮或弹层内部时保持弹层打开；Tab 离开整个扩展区域后关闭。

触摸行为：

- 触摸设备没有 hover 时，点击编号区域切换菜单。
- 点击菜单外部关闭菜单。
- 点击复制按钮只复制，不打开或关闭导航菜单。

### 6.3 菜单布局

菜单采用定稿的 A 版：

- 标题栏显示 `Open items` 和当前总数。
- 标题栏右侧显示“刷新列表”。
- 先显示 `Issues` 分组，再显示 `Merge requests` 分组。
- 每组标题显示资源类型和数量。
- 条目显示引用号和标题，标题过长时单行省略。
- Issue 引用号使用 GitLab 绿色系，MR 引用号使用紫色系；颜色不是唯一的信息来源，
  引用前缀和分组标题同时表达类型。
- 当前条目使用浅蓝背景、左侧强调线和“当前”标记。
- 当前条目不渲染链接、不响应点击、不响应 Enter/Space。
- 其他条目渲染为原生链接，点击后在当前标签页跳转到其 `web_url`。
- 菜单最大高度受视口约束，条目过多时内部滚动；不影响页面滚动。

## 7. 状态与错误处理

菜单包含以下状态：

| 状态 | 展示行为 |
| --- | --- |
| 未打开 | 仅显示固定标签，不发请求 |
| 加载中 | 显示菜单外框和加载提示，保留刷新入口但避免重复请求 |
| 成功 | 显示两组 Open 条目和总数 |
| 空列表 | 显示对应分组的空状态，不伪造条目 |
| 已关闭当前条目 | 不在 Open 列表插入当前条目，不显示当前高亮行 |
| 刷新中 | 保留旧列表，刷新图标进入忙碌状态 |
| 初次单组失败 | 显示成功组；失败组行内显示“无法加载”，不缓存部分结果 |
| 初次两组失败 | 两组分别显示“无法加载”，标题栏保留刷新入口 |
| 有旧数据时刷新失败 | 任一组失败都保留完整旧快照，并显示“刷新失败，显示上次结果” |
| 项目切换 | 关闭菜单并清理旧项目请求和快照 |

网络请求失败、JSON 结构异常、响应非 2xx 或分页请求中断时，都不能影响顶部编号和
复制按钮。旧请求完成后不得覆盖新项目、新页面或已销毁标签的状态。

## 8. 生命周期与并发控制

导航列表与现有复制反馈共享内容脚本生命周期，但使用独立的请求代数和菜单状态：

- 每次项目或页面上下文改变时，使旧列表请求失效。
- `destroy()` 时取消或忽略未完成请求，移除菜单和相关计时器。
- 同一项目的刷新请求使用最新请求结果；较早请求完成后不得覆盖较新快照。
- 菜单打开状态不因普通 DOM mutation 重复重置。
- SPA 导航到同项目其他条目时更新当前高亮；导航到非详情页时移除整个标签。

## 9. 实现边界

预计改动集中在以下文件：

- `src/parser.js`：扩展解析结果，返回 origin 和项目路径。
- `src/content.js`：渲染导航触发区和菜单，执行 API 请求、分页、缓存、刷新、跳转和
  菜单生命周期管理。
- `manifest.json`：保持现有 HTTP/HTTPS 内容脚本匹配和权限模型；不增加扩展权限。
- `tests/parser.test.js`：覆盖多层 namespace、旧式路径和项目路径解析。
- `tests/content.test.js`：覆盖渲染、hover/键盘状态、API 请求映射、缓存、刷新、当前
  条目禁用、错误和异步竞态。
- `tests/browser.test.js`：用本地 HTTP 测试服务器模拟 GitLab API，验证真实悬停、
  菜单、刷新按钮和跳转。
- `README.md` 与 `docs/testing.md`：补充导航行为、API 依赖、缓存和验收边界。

不引入第三方 UI 组件、网络客户端或状态管理库，沿用无构建步骤的 Manifest V3
内容脚本结构。

## 10. 测试与验收

### 10.1 单元测试

覆盖：

- 解析结果正确返回 origin、项目路径、kind 和 iid。
- 多层 namespace 和旧式 Issue/MR URL 构造正确 API 路径。
- 首次打开并行请求 Issue 和 MR，并正确传递 `state=opened`。
- `X-Next-Page` 分页直到完成，结果按 Issue/MR 分组。
- 其他条目生成正确的当前项目详情页地址。
- 当前 Open 条目高亮且不可点击；当前 Closed/Merged 条目不插入列表。
- 60 秒内重复打开复用缓存，刷新按钮强制重新请求。
- 刷新时保留旧列表，成功替换数据，失败保留旧列表并显示错误。
- 初次仅一组请求成功时显示成功组和失败组行内错误，且不缓存部分结果。
- 加载中、空列表、初次失败和项目切换状态正确。
- hover 延迟打开、离开延迟关闭、键盘打开/关闭和 Escape 行为正确。
- 旧项目或旧请求完成后不能污染当前菜单。

### 10.2 真实浏览器测试

通过本地测试服务器和真实 Chromium 验证：

- 悬停 `Issue #8` 后菜单自动出现，且复制按钮仍可独立点击。
- Issue/MR 两个分组、当前行高亮和不可点击行为符合设计。
- 点击其他 Issue/MR 后当前标签页跳转到正确详情 URL。
- 点击“刷新列表”时列表不闪空，API 请求重新发生。
- API 错误时编号和复制功能仍可使用，菜单显示可重试错误。
- 键盘聚焦、Enter/Space、Escape、菜单外部点击均符合预期。
- SPA 导航后当前高亮和项目缓存正确更新。

### 10.3 手工验收

在 Chrome 150、Arc 1.157.1 和真实自建 GitLab 中确认：

1. 悬停编号即可打开当前项目的 Open Issue/MR 列表，不需要下拉箭头或额外点击。
2. 当前条目清晰高亮但无法跳转，其他条目可正常跳转。
3. 刷新列表入口易于发现，刷新时不会清空已显示内容。
4. 私有项目遵循当前登录用户权限，不展示无权访问的条目。
5. 关闭或合并的当前条目不会被错误加入 Open 列表。
6. 列表加载失败时，顶部固定编号和复制按钮仍保持可用。

## 11. 完成标准

以下条件全部满足才算完成：

- 当前项目 Open Issue 和 Open MR 可从编号悬停菜单访问。
- Issue/MR 按组展示，其他条目可跳转，当前条目高亮且不可点击。
- 刷新列表可绕过缓存并正确处理成功、失败和旧数据保留。
- API 分页、权限、项目切换和 SPA 导航无陈旧数据或竞态污染。
- 不新增扩展权限、Token 配置、持久化数据或第三方运行时依赖。
- 单元测试、真实 Chromium 测试、文档和手工验收全部通过。
